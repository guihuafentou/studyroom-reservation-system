# 《校园自习室预约管理系统》设计方案评审报告

**评审视角**：高校信息系统架构评审　**文档版本**：v1.0　**评审日期**：2026-10-01

**总体结论**：方案结构完整、技术栈主流、文档规范，作为课程/毕设级系统已具备较好的完整度。但在**并发防冲突的正确性**、**视觉检测方案的物理可行性**、**数据库约束完备性**三方面存在会直接影响系统核心价值的问题，其中两处为「致命级」缺陷，需在实现前修正。

---

## 一、需求覆盖度评审

### 1.1 功能完整性：基本完整，存在 4 处业务盲区

已覆盖注册登录、座位地图、预约/取消/签到、管理端 CRUD、统计报表、视觉联动，主流程要素齐全。但以下业务点缺失：

| 盲区 | 说明 | 影响 |
|---|---|---|
| **无「同一时段仅允许预约一个座位」的约束** | 文档只约束「同一座位同一时段不可重复预约」，未约束「同一用户同一时段不可预约多个座位」 | 学生可同时抢多个自习室/多个座位，造成资源二次浪费 |
| **无违约惩戒机制** | 状态机有「4 违约」，但无「违约次数累计→限制预约/禁用」的后续规则 | 违约零成本，占座治理目标落空 |
| **无取消截止时间** | U5「未签到前可取消」无时间下限 | 学生可在时段开始前 1 分钟任意取消，座位无法流转 |
| **无预约时长上下限** | 采用自由 `start_time/end_time`，未定义最小/最大预约时长 | 可约 5 分钟，也可约全天，放大时间冲突问题 |

### 1.2 预约业务流程闭环性：主链路闭环，但「离座释放」语义不完整

「预约→签到→离座释放→已完成」链路在 6.2/6.3 有交代，但**关键缺口**：

- 用户中途离座被释放后，**该座位剩余时段是否可被他人再约、原用户是否损失剩余时长**均未定义；
- 状态机（4.3 节）中「离座释放→已完成」与「自然时段结束→已完成」共用同一状态，无法区分「提前结束」，后续统计上座率/违约率会失真。

**结论**：需求覆盖度 85%，闭环性 75%。建议补充「提前释放」子状态与用户侧规则。

## 二、架构合理性评审

### 2.1 前后端交互：合理

B/S 三层 + Vue3 + Spring Boot 3 + 统一返回结构 + JWT 无状态认证，范式正确。前端轮询座位地图（5.2 `/seats`）合理。

### 2.2 视觉识别集成方式：存在「致命缺陷」+ 一处文档自相矛盾

**致命缺陷 1——MOG2 背景建模与「治理占座」目标物理上矛盾**：

- MOG2 是**自适应背景建模**，会将长时间静止的前景目标逐渐「学习」进背景。这意味着：**安静看书的静止学生、放在桌上/椅上的书本水杯（恰恰是要治理的「占座物品」），静止一段时间后都会被判为「空座」**。
- 文档 3.3.1 对比表自己承认「帧差法：静止目标完全失效」，但 MOG2 对「长时间静止目标」存在**同类失效**，只是失效时间更长。文档声称的「检测人形区域」实际依赖目标持续运动，与自习室「人长时间静坐」的真实场景严重不匹配。
- 后果：核心卖点「疑似占座提醒」「离座释放」在静止场景下会大量误判，甚至把正常自习的学生误释放。

**致命缺陷 2——`/report`（推送）与「后端轮询」两种集成模式并存、文档自相矛盾**：

- 3.1 节「本设计采用**后端轮询**模式」；
- 3.3.2 检测流程却写「`POST /api/vision/report` 上报后端」；
- 5.4 接口表又同时列出 `GET /detect`（轮询）与 `POST /report`（上报）。
- 三处互相打架，实现时必然踩坑。**必须二选一**，并明确失败重试、去重、乱序处理策略。

### 2.3 扩展性：中等，方向正确但缺关键解耦

- `BaseDetector` 接口抽象 + `yolo_detector.py` 预留位（3.3.2）是正确做法，值得肯定。
- 但**座位状态只落 `occupied` 布尔 + `confidence`，未记录检测来源/版本**，切换检测器后无法追溯、无法灰度对比。建议在 `seat_status_log` 增加 `detector` 字段。
- 5s 轮询模式下，后端为**主动拉取方**，视觉服务无状态压力小，但扩展至多楼栋多摄像头后，轮询会被 `roomId` 遍历放大；若未来上目标检测，建议改回「推送+回调」模式。

**结论**：前后端架构合理，视觉集成模式需先统一；扩展性中等偏上。

## 三、数据库设计评审

### 3.1 表结构：整体合理，存在 3 处不一致

1. **`seat.status` 枚举与业务规则矛盾**：4.2.3 定义 status 为 `0禁用 1空闲 2使用中`，**没有「已预约」状态**；但 3.3.3 明确写「预约成功座位状态置为已预约」，6.1 也写「标记已预约」。状态机与字段枚举不一致，实现时需靠查询 reservation 表兜底，逻辑会割裂。
2. **`reservation.room_id` 冗余**：可由 `seat.room_id` 推导，存在数据不一致风险（虽利于查询）。若保留需在业务层强制校验 `seat.room_id == room_id`。
3. **`room.open_time/close_time` 用 `VARCHAR(5)` 存时间**：应改用 `TIME` 类型，否则无法做时间运算/排序校验。

### 3.2 索引与唯一约束：存在 2 处关键缺失

**关键缺陷 A——`uk_seat_time` 唯一索引无法防止「时段重叠」抢座（致命级）**：

- 4.2.4 唯一约束为 `(seat_id, reserve_date, start_time, end_time)`，**只能挡住「完全相同的起止时间」重复插入**。
- 反例：预约 A `09:00–11:00`，预约 B `10:00–12:00`——二者 start/end 均不同，唯一索引**不会触发**，B 正常插入，两个预约在 `10:00–11:00` 重叠。
- 这意味着文档 6.1 声称的「唯一索引 + 事务保证同一座位同一时段不被重复预约」**在自由时段模型下是错的**，并发抢座防护形同虚设。

**关键缺陷 B——`seat` 缺业务唯一约束**：

- 缺 `UNIQUE(room_id, seat_no)`：同一自习室可出现重复座位编号；
- 缺 `UNIQUE(room_id, row_no, col_no)`：座位图两个座位坐标可重叠。

### 3.3 其他风险点

| 项 | 问题 | 建议 |
|---|---|---|
| `seat_status_log` 无界增长 | 5s/座/次 → 单座 1.7 万行/天，100 座 = 170 万行/天，无分区、无清理策略 | 仅状态翻转时写 + 心跳，按日分区/定期归档 |
| 定时任务缺查询索引 | 6.3 违约扫描按 `status + 时间` 过滤，但索引只有 `idx_user`、`idx_seat_date` | 增加 `(status, reserve_date, start_time)` 复合索引 |
| 无操作审计表 | 管理员「强制取消」等敏感操作无留痕 | 增加 `admin_audit_log` |
| 外键未明确 | 标注 FK 但 MyBatis-Plus 常不建真外键 | 明确由应用层保证参照完整性 |

**结论**：表设计 70 分；`uk_seat_time` 的「重叠失效」与 seat 缺唯一约束是必须修复项。

## 四、风险与盲点

### 4.1 并发预约抢座（致命）
如上所述，自由时段 + 唯一索引**无法防重叠抢座**。即使采用「先查后插」，TOCTOU 竞态下两事务同时查到「无冲突」再插入，重叠预约双双成功。**必须在应用层用 `SELECT ... FOR UPDATE` 锁定座位行 + 显式重叠区间判断，或改为离散时段模型（见建议 1）。**

### 4.2 时间冲突（高）
- 自由起止时间导致重叠区间检测复杂（需 `start < other.end AND end > other.start` 判断）；
- 「预约时段须在自习室开放时间内」仅在 7.2 输入校验提及，**无服务端统一强制、无数据库级约束**，绕过前端即可预约闭馆时段；
- 后端与视觉服务时钟不同步会影响「超时未签到 30 分钟」判定，需 NTP。

### 4.3 占座治理（致命——与目标背离）
核心治理手段依赖 MOG2，但静止人/物会被吸收进背景，导致**「疑似占座」几乎无法被检测到**，占座治理目标实际上无法达成。这是「方案选型」层面的根本问题，而非实现细节。

### 4.4 摄像头场景限制（高）
- 固定机位 + 单摄像头多座位 ROI：透视遮挡、前后排互挡、侧身/低头（轮廓面积骤减）会导致 `0.5` 重叠阈值误判；
- 光照突变（开灯/阳光直射）MOG2 敏感，易产生大面积假前景；
- ROI 一次标定后，摄像头轻微移位即整体失效，缺「标定自检/告警」机制。

### 4.5 隐私合规（中）
- 「不存视频流、不采集人脸」的立场正确，值得肯定；
- 但「检测画面预览开关」会临时展示**原始画面**给管理员，存在人脸暴露风险，且自习室属半公共空间，需**现场张贴告示 + 预览默认关闭且加人脸打码**；
- `student_no` 为登录标识属个人信息，注册接口公开（5.1 `/register` 无验证），**未与学校学籍系统校验**，任何人都可注册为「学生」，身份真实性弱；
- `seat_status_log` 虽只存占用状态，但 5s 粒度可反推个人行为轨迹，建议明确保留期限。

### 4.6 其他（中低）
- **JWT HS256 无退出/吊销机制**：token 泄露后在过期前持续有效，建议加短时效 + 刷新令牌或黑名单；
- **视觉服务不可用时「同样置违约」**（6.3）不公平：技术故障不应惩罚学生，建议改为「释放但不计违约」；
- **离座释放 30 分钟阈值 + MOG2 静止失效**叠加，正常安静自习的学生可能被误释放，体验风险高。

## 五、改进建议清单（按优先级，可落地）

### P0（必须，影响正确性/可行性）

1. **重构时段模型，根治重叠抢座**：推荐引入离散时段表 `slot(id, start_time, end_time)`，预约改为 `reservation(slot_id)`，建唯一索引 `UNIQUE(seat_id, reserve_date, slot_id)`——离散时段下唯一索引才真正防并发；若坚持自由时段，则预约事务内先 `SELECT ... FOR UPDATE` 锁定 `seat` 行，再以 `start < :end AND end > :start` 判断重叠，并保留唯一索引兜底。
2. **修正视觉检测方案选型**：短期在 MOG2 上设 `learningRate=0` 并用「空场景静态背景」启动初始化 + 闭馆时段定时重基线；**中期直接切换到 YOLOv8（人 + 书本/水杯类别）做占用检测**，才能真正支撑「静止占座」判定。文档预留的 `yolo_detector.py` 应提前到主实现。
3. **统一视觉集成模式**：明确采用「视觉服务主动 `POST /api/vision/report` 推送」还是「后端轮询 `/detect`」，删除文档中矛盾表述，并定义去重（按 detect_time/seq）、失败重试与乱序处理。
4. **补充 seat 唯一约束**：`UNIQUE(room_id, seat_no)`、`UNIQUE(room_id, row_no, col_no)`，并统一 `seat.status` 与业务状态（增加「已预约」值或明确由 reservation 推导）。

### P1（强烈建议，影响业务闭环）

5. **补业务规则**：同一用户同一时段仅可预约 1 个座位（服务端强制）；定义最小/最大预约时长；定义取消截止时间（如开始前 30 分钟）；定义违约累计 → 限制预约的惩戒阶梯。
6. **增加 `(status, reserve_date, start_time)` 复合索引**，支撑违约/释放扫描任务。
7. **seat_status_log 治理**：仅在状态翻转时写库 + 低频心跳；按日分区，超过 N 天归档删除；增加 `detector` 字段。
8. **违约判定去技术化**：视觉不可用时「释放但不计违约」，避免系统故障惩罚学生；引入「系统不可用」标记。
9. **统一签到策略**：3.3.3 与 6.2 对「视觉空座时签到」的处理不一致，明确「视觉可用且空座→提示核实」「视觉不可用→按时间窗直接签到」两条路径。

### P2（建议，提升工程质量与合规）

10. **增加 `admin_audit_log` 审计表**，记录管理员强制取消、状态修改等敏感操作。
11. **JWT 加固**：缩短过期时间 + 刷新令牌或版本号吊销；密钥支持轮换。
12. **注册身份校验**：对接学籍/一卡通信息或邮箱验证，避免任意注册；登录/注册加验证码与限流。
13. **隐私落地**：预览默认关闭并加人脸/区域打码；自习室张贴监控告知；明确 `seat_status_log` 保留期限。
14. **时钟同步**：后端与视觉服务统一 NTP，消除超时判定误差。
15. **补重叠区间并发测试用例**：现有「并发测试」只测同起止时间，必须增加「部分重叠」「完全包含」两种抢座用例。

---

**一句话总结**：方案「骨架完整、卖点清晰」，但「唯一索引防并发」与「MOG2 治理占座」两处核心设计在技术上不成立，属于必须在编码前修正的方向性问题；修正后可作为合格的高校信息系统立项方案。
